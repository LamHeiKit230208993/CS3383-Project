01

The short version

A price helper that stays on your machine.

Market Desk is a single Spring Boot process with one local shopper, one H2 file and two external services. It turns a public price feed into exact-pack comparisons, then layers carts, budgets, wishlist tracking, alerts, reminders and a tool-calling assistant on top of the same records.

One local shopper

There is no account table, no login and no sync. The server binds 127.0.0.1, and LocalRequestGuard rejects non-local hostnames plus cross-site browser writes. Every record belongs to the same invisible user.

The catalogue is a snapshot

Prices enter only through an explicit LIVE, SAMPLE or DEMO import. One accepted_import row describes what is on screen. Missing products are deactivated, never deleted, so old carts and history keep valid references.

The assistant proposes; the app decides

Ask tools read checked rows and return proposals. Adding to a cart, creating a list and adding a wishlist item can apply immediately. Removals, deletes and every alert change wait for a Confirm click, and stale proposals are re-proposed rather than forced.

What it is

  • A local price comparison and shopping planner for Hong Kong groceries.
  • Exact-pack search across retailer listings, with unknown prices kept unknown.
  • Named carts, a weekly or monthly budget, and a versioned list transfer format.
  • Wishlist tracking, price history, watch rules, alerts and replenishment reminders.
  • A grounded AI assistant that can read local data and prepare changes.
  • An offline HTML checklist that needs no server connection to review.

What it is not

  • A multi-user service: no accounts, roles, sharing or live co-editing.
  • A checkout or purchase ledger: it never buys anything.
  • A stock, branch, district or delivery checker.
  • A background scraper: imports happen only when the shopper asks.
  • An open-ended agent: the model gets 11 bounded tools, not the database.
  • A cloud app: nothing leaves the machine except the price fetch and the chat request.
The constraint that explains most of the code

One local user, one process, one file database. That removes authentication, tenancy and distributed consistency from the design. The hard problems that remain are data replacement, deduplication and idempotence: an import must not duplicate alerts, a 60-second tick must not duplicate reminders, and a stale AI proposal must not overwrite a newer cart.

02

Architecture

One process, four layers, three edges.

The application is a conventional Spring MVC monolith, deliberately. Controllers stay thin, feature services own transactions, and every feature package maps its own entities into the same H2 file. Three edge components do the asynchronous or external work: the catalogue importer, the Ask tool loop and the 60-second scheduler.

Layer 01 · the client

Server-rendered pages, lightly enhanced.

Thymeleaf renders every page from the same market-desk.html shell. There is no SPA framework and no client-side router. Small vanilla modules add only the behaviour that benefits from it: the chat transcript, inline check-off, alert rule editing, the price chart and display settings.

Boundary behaviour

  • Normal links and form posts work without JavaScript.
  • fetch is used for the Ask reply loop and inline cart check-off.
  • Language and high-contrast mode are applied by the server on the next render.
  • The offline checklist is a separate, self-contained HTML download.

Layer 02 · HTTP entry points

Thin controllers, explicit redirects.

Controllers bind request parameters, reject invalid shapes, call a feature service and then choose a view or a redirect. They do not own pricing, alert or reminder rules. Flash messages carry success and error feedback across the post-redirect-get boundary.

Boundary behaviour

  • LocalRequestGuard rejects non-local hosts and cross-site writes before a controller runs.
  • DisplayLocaleResolver reads the saved language preference for every request.
  • Validation failures become flash errors and a safe redirect, not a stack trace page.
  • Ask is the one controller with a session state machine.

Layer 03 · the rules

Feature services own their transactions.

Each package owns a slice of the database and the rules that protect it. Services are the only place where multi-row invariants are enforced: one item per product per list, one enabled tracking period per product and retailer, one reminder occurrence per due time, one accepted import row.

Feature packages

catalogshoppingtrackingnotificationsreminderbudgetpreferencespersonal

Deliberate coupling

  • A LIVE import calls tracking, legacy targets and watch rules inside the replacement transaction.
  • Adding a reminder to the cart calls the shopping service rather than writing items itself.
  • Budget reads the shopping summary; it never stores a second copy of the cart.
  • Personal data reaches across packages only to delete or export, never to change rules.

Layer 04 · stored state

One file, eighteen entities, explicit keys.

Spring Data JPA repositories sit behind every service. The database is an H2 file at ./data/pricewatch; schema updates use ddl-auto=update. Open-session-in-view is off, so each service method must load what it needs inside its transaction.

Storage rules

DECIMAL(19,4)90-day observationssingleton settingsunique constraintsno FK for some references

Why it matters

  • Prices and limits use fixed-point decimals, never floating point.
  • Alert and reminder history can outlive the rule that created it.
  • Selected retailer codes and rule product codes are deliberately not foreign keys.
  • Deleting the file is a full reset; the Personal data page is a selective reset.

Layer 05 · outside the request

Three edges, each with a hard boundary.

Nothing runs continuously except the scheduler. The feed is fetched only on a LIVE import, the LLM is called only during an Ask turn, and the scheduler runs a fixed-delay tick every 60 seconds while the web application is active.

Edge components

ConsumerCouncilSourceClientDeepSeekChatClientNotificationScheduler

Boundary behaviour

  • Feed fetch: 30-second timeout, 10 MB cap, parsed and validated before replacement.
  • LLM call: optional API key, 30-second turn budget, 3 tool rounds and 8 tool calls.
  • Scheduler: disabled with pricewatch.jobs.enabled=false; times use Asia/Hong_Kong.
  • Offline mode is a downloaded file, not a service worker or a second runtime.
The one cross-feature transaction to remember

CatalogReplacementService.replace() is @Transactional. For a LIVE import it calls TrackingService.recordLiveImport(), then the legacy target evaluator and then WatchRuleService.evaluateLive() before saving the accepted-import row. A single refresh can therefore append observations, create retailer alerts, fire watch rules and update the catalogue as one atomic unit.

Domain model · UML

What the system knows.

Scope first, then schema. The use-case diagram shows the single actor and the three external participants. The class diagrams split the persistent model in two because the catalogue side and the tracking side change for different reasons — and because fitting eighteen entities on one plate would explain nothing.

Reading the model

Keys are the story.

The catalogue is keyed by the public product code. A cart row is unique on (list, product). A tracking period is unique on (product, retailer, enabled). A reminder occurrence is unique on (reminder, dueAt). Those four keys are what make imports, carts and the 60-second tick idempotent.

Some references are deliberately soft. WatchRuleEntity.productCode, ReminderOccurrenceEntity.reminderId and AlertEventEntity.observationId are plain values, not foreign keys, so history survives deletion of the row that produced it.

Invariant 01

One row per product per list

Adding the same product again updates quantity and retailer instead of appending a duplicate. Quantity is clamped to 1–999.

Invariant 02

Unknown is not zero

A listing with no price contributes to the unknown count. It is excluded from the known subtotal and from any automatic-lowest decision.

Invariant 03

Deactivate, never delete

A product missing from the latest accepted import becomes active = false. Cart rows, observations and alert history keep their references.

Three alert mechanisms, one page

AlertEventEntity holds legacy retailer target/drop/summary alerts tied to a tracking period. ProductTargetEventEntity holds events from per-product targets and unified watch rules. ReminderOccurrenceEntity holds replenishment occurrences. AlertCenterController reads all three and merges them into one dated timeline, newest first.

Watch rule

Price, calendar or both

One table covers all three shapes. A price condition needs the product on the wishlist; a calendar condition does not. One-time rules complete after firing; repeating rules re-arm.

Retention

90 days of observations

Old observations are pruned, but dedup state is kept so a re-import cannot recreate an alert that was already shown.

Settings

Singletons with id = 1

Budget, notification quiet hours and display preferences each have exactly one row. Personal-data reset deletes them and recreates defaults on next use.

05

Workflows · UML sequence diagrams

Four paths through the system.

Each diagram is a real code path, not an aspirational sketch. Read them in order: how prices arrive, how a cart is priced and moved, how the clock produces alerts, and how one assistant turn is bounded and confirmed.

What to notice

  1. Fetch is outside the transaction. The 30-second HTTP call and the 10 MB validation happen before replace() starts, so a slow network never holds database locks.
  2. Replacement is destructive first. Offers and listings are deleted and products deactivated before the new snapshot is inserted. The accepted-import row is saved last, so it never describes a half-written catalogue.
  3. LIVE has side effects. Only LIVE calls recordLiveImport() and evaluateLive(). SAMPLE and DEMO load data without inventing price movement.
  4. Dedup happens downstream. Observation append is skipped when the price is unchanged; alert and reminder inserts rely on unique keys.
  5. Checksum is provenance, not identity. It records what was fetched; the import is not skipped merely because the checksum matches.

SAMPLE and DEMO require an explicit confirmation when a catalogue already exists. LIVE does too — refresh is never implicit.

What to notice

  1. Retailer choice is explicit or automatic. A supplied retailer must have a known price for that product; otherwise the add is rejected. A null retailer resolves to the lowest known price at render time.
  2. Upsert, not append. The unique (list, product) row means adding again changes quantity. The main list is named “My list” and cannot be renamed or deleted.
  3. Transfer is versioned and bounded. JSON version 1, at most 1 MB and 1,000 rows. The whole file is validated before anything is written.
  4. Unresolved codes are preserved. An imported row whose product is not in the catalogue is kept as an unresolved reference rather than silently dropped.
  5. Offline is a render, not a sync. The checklist is generated once with inline CSS and no live calls; reopening it cannot change the cart.

Known subtotal = sum of known price × quantity. Unknown rows are counted separately and never treated as free.

What to notice

  1. Price alerts are import-driven. Tracking evaluates target and drop rules when a LIVE import appends a changed observation. No import means no new price event.
  2. Calendar alerts are clock-driven. WatchRuleService.checkDue() runs every 60 seconds and advances the next due time when it fires.
  3. Waiting for LIVE is a state. A due price rule with no accepted LIVE price calls waitForLive() instead of firing on SAMPLE or DEMO data.
  4. The tick is idempotent. recordDue() inserts at most one occurrence per (reminder, dueAt); repeating the tick cannot duplicate a reminder.
  5. One timeline, three sources. The alerts page reads legacy alerts, watch events and reminder occurrences, then groups them by date and trigger.

Quiet hours and the daily summary time live in NotificationSettingsEntity (id = 1) and apply to notifications, not to evaluation.

What to notice

  1. Send and reply are separate requests. /ask/send appends the question and returns a redirect; the page then fetches /ask/reply, which claims the turn and calls the model.
  2. The loop is capped. At most 3 tool rounds, 8 tool calls, 30 seconds per turn and 4,096 characters of tool arguments. The client keeps the last 9 messages plus the system instructions.
  3. Tools read checked data. Catalogue and shopping tools call the same services as the pages; they never see SQL or raw entities.
  4. Proposals, not arbitrary writes. The model can request a change; the controller decides whether to apply it now or ask for confirmation.
  5. Stale is a first-class outcome. If the cart or list changed since the proposal, confirming it produces a fresh proposal instead of overwriting newer data.

A missing API key or a slow/failed turn leaves the chat in a retryable state. The page polls /ask/reply up to 30 times at 500 ms.

The AI layer

A bounded assistant, not an agent.

Ask is a chat surface wrapped around eleven typed tools and a session state machine. The model can read the same data the pages read and prepare the same writes the forms perform — but every write passes through a controller that decides whether it applies now or waits for a click.

The turn, as a state machine

READYNo reply in flight. The composer is enabled.idle
WAITINGThe question is stored; the page is about to fetch the reply.accepted
REPLYINGOne request has claimed the turn and is calling the model.claimed once

The transition back to READY happens only after the answer, cards and proposals are appended. A failed or slow turn returns to WAITING so /ask/retry can try again without duplicating the question.

07

Runtime rules

The clock, the imports and the invariants.

Most of the system's character is in its rules: what an import may change, what the 60-second tick may create, and what “reset” actually deletes. These are the details that decide whether the app is trustworthy after a month of use.

One tick, every 60 seconds

+0 sfixed delay

Record due reminders

reminders.recordDue() finds rules whose nextDueAt has passed and inserts an occurrence. The unique (reminder, dueAt) key makes a repeated tick a no-op.

+0 ssame tick

Evaluate watch rules

watchRules.checkDue() reads due rules and the latest accepted LIVE prices. Calendar rules fire without a price; price rules without an accepted LIVE price call waitForLive().

+60 snext run

Wait for the next fixed delay

The delay is measured after the previous run finishes, not on wall-clock boundaries. Disable it with pricewatch.jobs.enabled=false.

neverthe scheduler

Does not fetch prices

There is no background scraper. A new price enters only through a manual LIVE import, so the timeline cannot change while the shopper is asleep.

Cart rule

Quantity 1–999

Invalid quantities are clamped or rejected before the write. The main list cannot be renamed or deleted, and one product appears once per list.

Price rule

Unknown ≠ free

Unknown prices are excluded from the known subtotal, shown as a separate count, and never chosen as the automatic lowest price.

Tracking rule

One enabled period

A product and retailer pair has at most one enabled tracking period. Starting again reuses or reopens it rather than stacking duplicates.

Watch rule

Price needs wishlist

A price condition requires the product on the Wishlist. A calendar-only rule does not. One-time rules complete; repeating rules re-arm.

Reminder rule

One occurrence per due time

Clear advances the next due date; snooze adds 24 hours to the current occurrence. Deleting a rule keeps its occurrence history.

Privacy rule

Reset keeps the catalogue

PersonalDataService.reset() deletes personal tables and preferences, but keeps products and listings. Deleting the H2 file is the full reset.

Local security

Trust is a network boundary.

LocalRequestGuard rejects requests whose host is not local and rejects cross-site browser writes. The server binds 127.0.0.1. There is no login because there is no remote user to authenticate — but the guard still blocks a malicious page from posting to the local app.

Personal data

Export everything, reset selectively.

One JSON export covers lists, items, wishlist, tracking, observations, alerts, reminders, budget, preferences and the chat transcripts passed from the session. Reset removes those rows, recreates defaults lazily, and prunes inactive products that only existed to satisfy imported list references.

Run & verify

From clone to first import.

The app needs Java 21 and Maven. It starts on 127.0.0.1:8080 with an empty file database; the first useful step is a SAMPLE or DEMO import. Ask additionally needs a course API key.

Start the app

mvn spring-boot:run
$env:DEEPSEEK_API_KEY_SKU = "…"

Set the key in the same shell before starting if you want Ask. The rest of the app works without it.

Run the checks

mvn test
npm install && npx playwright install chromium
npm test

The Playwright suite drives the running app. Start the server first, then run the browser checks.

First-run checklist

StepWhat to verify
01 · Open /The empty state explains that a catalogue is needed; no stack trace.
02 · Import SAMPLECounts appear on /data; search returns exact packs.
03 · Add to cartThe row appears once; quantity updates instead of duplicating.
04 · Set a budgetKnown subtotal, unknown count and remaining amount agree.
05 · Save + trackThe wishlist entry appears; tracking opens one period per retailer.
06 · Import LIVENew observations appear only for changed prices.
07 · Create a ruleA calendar rule fires without a wishlist; a price rule requires one.
08 · Wait one tickDue reminders appear once, not once per tick.
09 · Export / resetThe JSON download contains personal data; reset keeps the catalogue.
10 · Ask (optional)Without a key, a clear configuration message; with a key, a grounded answer.
Where the time goes

The slowest paths are the LIVE fetch (network, 30-second cap) and one Ask turn (model latency, 30-second budget). Everything else is a local H2 read or write. If a page feels slow, check whether it is waiting on one of those two edges before optimizing the database.
